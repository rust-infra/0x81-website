日期：2026-10-02
状态：待确认
配套：`2026-10-02-rehearse-design.md`（技术设计）、`2026-10-02-gateway-auth-design.md`（统一认证）、`rehearse-app/design/index.html`（UI 设计稿）

## 1. 一句话

> **职演 Rehearse —— 在你真正开口之前，先演一遍。**

给即将面对一次具体职场对话的人（面试、晋升答辩、汇报、高压沟通），提供一个**随时在、能扮演对手、会追问、还告诉你哪里说错了**的练习对象。

## 2. 用户

### 2.1 不是「想学英语的人」

这是这个产品最容易走偏的地方。职演的用户**不是为了提升某项长期能力**，而是**为了一次有具体时间点和结果的对话**。

| 用户 | 触发时刻 | 窗口 |
|---|---|---|
| **求职者**（主要） | 收到面试通知 | 3–14 天 |
| **在职者面临关键沟通** | 晋升答辩通知、绩效季、要向老板要资源、要拒绝一个不合理需求 | 1–7 天 |
| **需要英文开会的人** | 加入外企 / 远程团队，下周要主持英文周会 | 持续，但每次会议前集中 |

**共同点：有 deadline，有结果，且没有低成本的练习方式。**

### 2.2 不是「每天来打卡」

墨言的循环是高频轻量（每天背几个词）。**职演是低频重量**——用户来一阵子，事情过去了就走。

这个差异决定了三件事：

1. **不做每日打卡 / 连续天数**——那是墨言的留存机制，搬到职演上会显得荒谬（「连续 7 天模拟面试」？）
2. **通知不是「该练了」，是「面试还有 3 天」**——事件驱动，不是习惯驱动
3. **要能「上次练到哪」**——用户中断几天回来，需要一眼看到上次的总结和改进点

## 3. 问题定义

### 3.1 现有做法都不够

| 现有做法 | 缺口 |
|---|---|
| 找朋友 / 同事模拟 | 约不到、欠人情、**不能重复练同一个问题**、对方不会追问到底 |
| 对着镜子或录音 | 练了，但**不知道哪句说错了**——没有反馈的练习只是重复错误 |
| 看面经、背答案 | 被动输入，不开口；真实对话里**接不住追问** |
| 付费陪练 / 机构 | 几百到几千一次，要预约，时间不自由；且**往往只做一次** |
| 通用 AI 聊天 | 会陪你聊，但**不会扮演一个会追问你的面试官**，也**不纠你** |

### 3.2 核心缺口

> **缺一个随时在、能扮演对手、会追问、还告诉你哪里说错了的练习对象。**

现有方案要么有「对手」没有「反馈」（朋友、付费陪练），要么有「反馈」没有「对手」（面经、录音回放），要么两个都没有（通用 AI 聊天）。

### 3.3 为什么是现在

- 语音识别与合成已经到了设备端免费、可用的程度（`expo-speech` / `expo-speech-recognition`），**音频零成本**
- LLM 能在一次调用里同时产出「对手的回应」和「对用户这句话的纠错」——这是过去做不到的
- 一次 10 分钟演练的模型成本，比一次真人模拟面试便宜三到四个数量级

## 4. 价值主张

> **把一个「会追问的对手」和一个「会纠错的教练」装进同一个对话里。**

一句话测试：如果只能保留一个功能，保留**逐轮纠错**——因为「有个东西陪我说话」这件事，用户拿通用 AI 聊天也能做到，而「说完之后立刻知道哪里说得不对」是职演独有的。

## 5. 功能范围

### 5.1 v1（MVP）

| 模块 | 内容 | 为什么在 v1 |
|---|---|---|
| **场景库** | 4 族 14 个预置场景（§6） | 用户不知道「该练什么」，必须给现成的 |
| **中英双语对等** | 每个场景可切演练语言 | 中文面试是主场；英文是真实需求但不是唯一 |
| **语音对话** | 设备端 STT + TTS | 「开口说」是产品定义的一部分，不是可选项 |
| **逐轮纠错** | 纠错 + 更自然的说法 + 中文解释 | **核心价值**（§4） |
| **接下来可以怎么说** | 针对 AI 最新一句给出的示范回应 | 解决「卡住不知道接什么」——这是放弃率最高的时刻 |
| **会话总结** | 亮点 / 待改进 / 推荐句型 | 让一次练习**留下可回看的东西** |
| **材料导入** | 简历 / JD → 可校对文本 → 紧凑档案 | 让追问「针对这个人这个岗」，是付费点（§8） |
| **自定义场景** | 从预置复制改，或一句话生成草稿 | 真实职场对话千变万化，14 个场景盖不住 |
| **本地历史** | 演练记录与总结回看 | 支撑「来一阵子」的用法（§2.2） |
| **文字兜底** | 麦克风不可用 / 权限被拒时打字 | 不让一个权限问题堵死整个产品 |

### 5.2 v1.5

- **系统分享入口**（iOS Share Extension / Android `ACTION_SEND`）——在电脑上看到 JD 直接分享进来，绕开「存文件 → 找文件 → 选文件」
- 场景族扩充（校园招聘、跨文化沟通）
- 总结导出（图片 / PDF）

### 5.3 明确不做

| 不做 | 理由 |
|---|---|
| 实时数字人 / 唇形同步 / 视频 | 按分钟计费，一次会话成本比纯文本高一到两个数量级。**只买沉浸感，不提升纠错与总结的价值** |
| 音素级发音评分 | 是「英语学习」的需求，不是「职场演练」的。做它会把产品拉回墨言的定位 |
| 真人 / 多人模拟 | 那就不是这个产品了 |
| 社区分享 / 场景市场 | 用户量不足以支撑；且职场场景涉及隐私，分享动机弱 |
| Web 端 | 2026-10-02 决定（见设计稿 §10） |
| 每日打卡 / 连续天数 | 与「低频重量」的用法冲突（§2.2） |
| 摄像头 | 只用于拍摄纸质材料，不做视频模拟 |

## 6. 场景体系

### 6.1 四个族

| 族 | 覆盖什么 | 数量 |
|---|---|---|
| `interview` 面试 | 求职、转岗、晋升面 | 4 |
| `pitch` 汇报与答辩 | 周会、项目评审、晋升答辩 | 3 |
| `hard_talk` 高压对话 | 拒绝需求、给负面反馈、承认失误、要资源 | 3 |
| `daily` 日常协作 | 站会、code review、跨时区沟通、茶水间 | 4 |

**为什么是这四族而不是更多**：族的划分要能回答「用户带着什么问题来」。面试是「我要拿到这个机会」，汇报是「我要说服别人」，高压对话是「我要把难听的话说好」，日常协作是「我要把工作推进下去」。四个已经覆盖了绝大多数场景，再多就会变成「什么都能装」的大杂烩。

### 6.2 场景不是「话题」，是「对手 + 处境」

一个场景必须能回答：

- **对手是谁**（姓名、职位、语气）——不是「AI 面试官」，是「陈磊，技术总监，说话直接」
- **处境是什么**（会议 / 一对一 / 电话 / 茶水间）
- **开场白是什么**（AI 说的第一句）
- **练习重点是什么**（3–5 项，例如「进度 / 阻塞 / 下一步」）
- **难度**（easy / core / challenge）

这五项缺一个，对话就会退化成「和 AI 闲聊」。

### 6.3 场景 × 语言是正交的

场景带一个**默认语言**（HR 初筛默认中文，远程茶水间默认英文），用户开始前可切。所以 14 个场景实际覆盖 14 × 5 种语言组合，不需要为「中文面试」「英文面试」各建一套场景。

## 7. 用户旅程

```
D-7  收到面试通知
       │
       ▼
     下载职演 ──► 登录（auth.0x81.uk，墨言账号直接登，不用注册）
       │
       ▼
     导入材料：上传简历 + 粘贴 JD
       │  ① 识别 → ②【用户校对 + 删敏感信息】→ ③ 生成档案
       ▼
     选场景：HR 初筛（中文）
       │
       ▼
     演练 8 轮 ──► 每轮拿到纠错
       │            └─ 卡住时看「接下来可以怎么说」
       ▼
     总结：3 个待改进 + 推荐句型 ──► 存本地
       │
D-5  再练一次：行为面 STAR（英文，同一个档案）
       │
       ▼
D-1  回看上次总结，只看「待改进」那三条
       │
       ▼
D-Day 面试
```

### 7.1 旅程里的三个关键决策点

**① 材料导入的校对闸门。** 识别一定有错，而错的地方（英文姓名、时间、数字）恰恰是面试官会追问的。**这一环的流失率是整个产品最高的风险**——用户要在手机小屏上逐字核对一份 800 字的简历。设计稿 §10 专门处理这件事。

**② 「卡住」的时刻。** 用户说到一半不知道下一句接什么，这是放弃率最高的点。所以「接下来可以怎么说」**不是纠错功能的一部分，它是防流失功能**——而且它在沉浸模式下也要显示。

**③ 第一次演练之后的总结。** 用户第一次练完，唯一带走的东西就是总结页。如果总结只是「说得不错，继续加油」，用户不会来第二次。总结必须给**具体的、可执行的**改进点。

### 7.2 回访的设计

因为用户是「来一阵子」，回访入口要围绕**事件**而不是**习惯**：

- 首页顶部：**「面试还有 3 天」**（如果有材料档案且用户填了面试日期）
- 最近一次总结的「待改进」直接摊在首页，不用点进去
- 不做连续天数、不做每日提醒

## 8. 商业化

### 8.1 付费点

| 层 | 内容 |
|---|---|
| **免费** | 预置场景演练、逐轮纠错、总结、本地历史。每日场次有上限 |
| **订阅** | 无限场次 · **材料导入（简历/JD 档案）** · 完整复盘导出 · 自定义场景数量不设限 |

**核心付费点是材料导入**，不是「无限次」。理由：次数对「低频重量」的产品不是稀缺资源（用户一周练 3 次，给 100 次和无限次没区别）；而**针对「我这个人这个岗」的演练**是用户能直接感知到的价值差异——面试官追问「你在 XX 项目里说主导，具体做了什么」，和追问泛泛的问题，体验完全不同。

定价锚点：一次真人模拟面试 300–800 元，一次 AI 模拟面试的订阅价要显著低于这个数才有说服力。

### 8.2 ⚠️ 现有额度设计与商业化冲突

设计稿 §7.7 沿用了墨言的默认值：**100 次 / 用户 / 天**。

这个数字在职演上**没有商业意义**：

- 它太高了——用户一周用 3 次，100 次/天等于无限
- 它又太低了吗？不，它的问题是**它不是一个付费点**，而产品却把它当成成本护栏

**建议改成两件事分开：**

| 维度 | 用途 | 建议值 |
|---|---|---|
| **成本护栏**（防滥用） | 防脚本刷、防极端用量 | 保留一个高的日上限（如 50 次/天），普通用户永远碰不到 |
| **商业额度**（免费层） | 区分免费与付费 | 免费层 **3 场/天**（一场 = 一次完整演练，不是一次发言轮次） |

**计量单位也要改**：现在是「用户发言轮次」，那是实现细节；用户能理解的是**「场」**。

> 这条要 Rg 拍板。改的话设计稿 §7.7 和管理后台都要跟着改。

## 9. 成功指标

因为低频，**不看 DAU**。

| 指标 | 定义 | 目标 |
|---|---|---|
| **激活率** | 安装 → 完成第一次完整演练 | ≥ 40% |
| **首周场次** | 7 天内完成的演练场次 | ≥ 3 |
| **单场轮数** | 一次演练的平均发言轮数 | ≥ 6（低于 4 说明对话没接住，或用户提前放弃） |
| **材料导入 → 开练** | 生成档案后 48h 内是否开始演练 | ≥ 70% |
| **事件回访** | 有档案的用户在导入后 7 天内回来第二次 | ≥ 50% |
| **付费转化** | 材料导入的付费转化率 | 待定（先测） |

**反面指标（要盯住的坏信号）：**

- 单场轮数 < 4 的比例——说明「卡住」的时刻没被接住
- 材料确认页的退出率——说明手机端校对的摩擦太大（设计稿 §10.3 的判据）
- 总结页的停留时长 < 10 秒——说明总结没有价值

## 10. 与墨言的关系

```
        0x81 账号体系（共享 users 表 / auth.0x81.uk）
              │
   ┌──────────┴──────────┐
   ▼                     ▼
墨言 MoYan            职演 Rehearse
词汇 / 打字 / 播客     职场演练
   │                     │
   └── 首页导流卡 ──────►┘
```

- **共享账号**：墨言用户装职演直接登，零摩擦
- **墨言首页放导流卡**：文案指向场景（「要去面试？先演一遍」），不是功能（「试试 AI 陪练」）
- **不做反向导流**：职演用户不需要去背单词，那不是他的旅程
- **共享后端进程与数据库**（当前实现），但**产品上完全独立**——这是拆分的全部意义

## 11. 风险

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| **冷启动** | 高 | 独立 App 拿不到墨言的用户池。缓解：首页导流 + 共享账号（§10）。**这是最大的风险，且不是技术问题** |
| **材料校对在手机上流失** | 高 | 用户要在小屏上逐字核对 800 字简历。缓解见设计稿 §10.2；真机实测后若仍流失，收窄为「只粘贴文本」 |
| **定位太宽** | 中 | 「职场演练」什么都能装。缓解：v1 锁死 4 族 14 场景，加族要走评审 |
| **用户不知道自己该练什么** | 中 | 缓解：材料导入（针对你的简历和 JD）+ 场景族的四问划分（§6.1） |
| **一次就走的用户** | 中 | 低频产品天然如此。缓解：让总结留下可回看的东西（§7.1 ③），用事件（面试倒计时）而不是习惯拉回访 |
| **中文演练的 prompt 质量** | 中 | 中文纠的是「表达策略」，英文纠的是「语言正确性」，是两套维度，不能复用同一模板（设计稿 §4.4） |

| 阶段 | 内容 | 判定标准 |
|---|---|---|

| **M2 App 文字版** | 场景选择 + 文字对话 + 逐轮纠错 + 总结 | 能用文字完成一次完整演练 |

**M2 完成即可内测**——先验证「逐轮纠错有没有用」这个核心假设，再投入语音体验。

## 13. 待确认

1. **免费层的额度口径**（§8.2）——建议从「100 次发言轮次/天」改为「3 场/天」，计量单位改成「场」。**要拍板**，因为会连带改设计稿和管理后台
2. **订阅定价**——本稿只给了锚点（显著低于真人模拟面试的 300–800 元），具体数字待定
3. **是否做「面试倒计时」**（§7.2）——需要用户填面试日期，多一步输入换更强的回访驱动。倾向做，但可能影响首次体验的顺畅度
4. **场景族要不要扩到 5 个**（加「校园招聘」）——v1 建议锁 4 个，观察数据再说
5. **是否要在 v1 就埋点**——本稿的指标都需要埋点，但设计稿里没有埋点章节。倾向 v1 就埋（否则 §9 全是空话）
6. **产品名的英文拼写**——`Rehearse` 还是 `Rehearsal`？前者是动词（更贴「演一遍」的动作），后者是名词。**默认 `Rehearse`**
